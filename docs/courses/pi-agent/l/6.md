# 进程与子进程：Agent 跑命令的能力

**阶段 0 · 模块 B（Node.js 核心）· 第 6 课 ｜ 预计 40 分钟 ｜ 前置：第 5 课**

> 本文为站内全文版（已纳入搜索，随堂测为折叠核对）。随堂测可点击作答的交互版：[**打开讲义**](/blog/lessons/pi-agent/lessons/0006-nodejs-child-process.html){target="_blank"}

这节课结束时，你的注册表里会多出第三个真实工具：`run_command`——让程序替你跑一条终端命令（比如 `npm test`、`git diff`），并把结果拿回来。这是 Coding Agent 最强大、也最危险的能力。

::: info 为什么学这个 · Mission 关联

Coding Agent 改完代码之后干什么？**跑测试、跑构建、看 git diff**——全靠启动子进程。pi 的 `bash` 工具、Kimi Code 跑命令时弹出的权限确认，底层全是 Node 的 `child_process` 模块。PatchPilot 出口标准里的"改代码 → 跑测试 → diff"闭环，这节课补齐最后一块基石。

:::

## 温故：先回忆，再学新内容

**1.（第 4 课复测）不看答案：`readFile` 返回 `Promise<string>`，忘了写 `await` 时 `console.log` 打出什么？`await` 做了哪两件事？**

::: details 显示答案

打出 `Promise { <pending> }`——小票本身，不是文件内容。`await` 做两件事：**等 Promise 兑现**（只暂停当前函数，不冻住整个程序）＋**把结果从小票里取出来**。

:::

**2.（第 1 课复测）`'${name}'`、`"${name}"`、``${name}``——哪种引号会把 `name` 替换成变量的值？另外两种打出什么？**

::: details 显示答案

只有**反引号**（模板字符串）会替换。单引号和双引号都是普通字符串，会把 `${name}` 四个字符原样打出来。

:::

**3.（第 5 课）`writeFile` 写一个已存在的文件，旧内容会怎样？真实 Agent 为什么不敢直接整文件覆盖？**

::: details 显示答案

旧内容被**直接覆盖**——不追加、不备份。所以真实 Agent 的"改文件"工具用 diff / 补丁机制保护现场（pi 的 `apply_patch`），阶段 1+2 会学到。

:::

## 1. 进程：正在运行的程序，就是一个进程

你在终端敲 `npm run start`，操作系统启动 tsx，tsx 跑起你的 `main.ts`——这个**正在运行的程序实例**，就叫一个**进程**（process）。进程是操作系统分配资源的单位：每个进程有自己的内存，彼此隔离。

关键动作来了：你的进程可以让操作系统**再启动一个程序**——比如跑 `node -v`、`npm test`、`git diff`。被你启动的那个新进程，叫**子进程**（child process）；你是它的父进程。父进程能看到子进程的输出，也能知道它跑得成不成功。

Agent 干的重活全在子进程里：跑测试看改对没有、跑构建看能不能编译、跑 git 看改了哪些行。不会启动子进程的 Agent，只是个聊天机器人。

## 2. exec + promisify：让"跑命令"返回 Promise

Node 把启动子进程的能力收在内置模块 `child_process` 里。我们用它最简单的一个函数 `exec`（execute，执行）：

```
<code>import { exec } from "node:child_process";
import { promisify } from "node:util";

const execAsync = promisify(exec);

const { stdout, stderr } = await execAsync("node -v");
console.log(stdout);   // v22.…（你机器上的 Node 版本号）</code>
```

逐行读：

- `exec` 是**回调风格**的老 API：它不返回 Promise，而是命令跑完后"打电话通知你"。第 4 课学的 `await` 没法直接用在它身上。
- `promisify`（`node:util` 模块）是一台**转换器**：吃进一个回调式函数，吐出一个**返回 Promise 的函数**。转换结果存进 `execAsync`——从此跑命令也能 `await` 了。
- `await execAsync(...)` 取出的结果是一个对象，装着 `stdout` 和 `stderr` 两个字段。`{ stdout, stderr } = ...` 这种写法叫**解构**：把对象里的两个字段直接拆成两个同名变量。

## 3. 命令结果三件套：stdout / stderr / 退出码

一条命令跑完，你实际拿到三样东西：

- `stdout`（standard output，标准输出）：命令的**正常输出**。`node -v` 打印的版本号就走这里。
- `stderr`（standard error，标准错误）：命令的**错误输出**。命令出错时的抱怨走这里——注意，报错文字在 stderr 里，**不在 stdout 里**，只看 stdout 会漏掉失败原因。
- **退出码**（exit code）：命令结束时向操作系统报告的一个数字。**0 = 成功**；**非 0 = 失败**，具体数字的含义由程序自己定（1、2、127 都可能）。

`exec` 的规矩：退出码非 0 → Promise 直接 **rejected**。被 reject 时，错误对象上挂着 `code`（退出码）、`stdout`、`stderr` 三个字段。所以第 5 课的 `try / catch` 原样搬过来用：

```
<code>try {
  const { stdout } = await execAsync("node -v");
  console.log("成功：", stdout);
} catch (error: any) {
  console.log("失败，退出码：", error.code);
  console.log("错误输出：", error.stderr);
}</code>
```

新语法一处：`catch` 后面括号里可以接一个变量名，把被抛出的**错误对象**接住——第 5 课用 `catch {` 不接，是因为当时不需要看错误内容；这次我们要读 `error.code` 和 `error.stderr`，所以接。错误对象的形状由 Node 决定，暂时用 `any` 标注，以后学了类型守卫再收紧。

::: info Windows 小提示

`exec` 在 Windows 上通过 cmd.exe 执行命令。这节课用的 `node -v`、`npm -v` 全平台通用；但 `ls`（Mac/Linux）和 `dir`（Windows）这类命令各系统不一样——先记住有这回事，真遇到再查。

:::

## 4. 动手：给注册表加 run_command 工具

**第一步**，`tools.ts`：顶部加两行 import 和一行转换，再加一个工具：

```
<code>import { exec } from "node:child_process";
import { promisify } from "node:util";

const execAsync = promisify(exec);

export const commandRunner: Tool = {
  name: "run_command",
  description: "运行一条终端命令，返回它的输出",
  execute: async (args) => {
    try {
      const { stdout, stderr } = await execAsync(args.command);
      return stdout.trim() || stderr.trim() || "（命令成功，没有输出）";
    } catch (error: any) {
      return `错误：命令失败，退出码 ${error.code}\n${error.stderr}`;
    }
  }
};</code>
```

注意它和第 5 课 `fileReader` 一模一样的设计：**失败不抛错，把失败原因（退出码 + 错误输出）作为工具结果返回**——模型看到"退出码 1 + 报错文字"，自己决定下一步，整个 Agent 不崩。

**第二步**，`main.ts`：注册工具，然后在 `main()` 里跑两条命令——一条成功的、一条注定失败的：

```
<code>import { calculator, greeter, slowGreeter, fileReader, fileWriter, commandRunner } from "./tools";

const toolRegistry: Record<string, Tool> = {
  calculator,
  greeter,
  "slow-greeter": slowGreeter,
  "read_file": fileReader,
  "write_file": fileWriter,
  "run_command": commandRunner,
};</code>
```

```
<code>// main() 里，文件读写那三行之后加：
console.log(await runTool("run_command", { command: "node -v" }));
console.log(await runTool("run_command", { command: "不存在的命令xyz" }));</code>
```

1. 按上面两步改造 `tools.ts` / `main.ts`。
2. 运行 `npm run start`：看到 Node 版本号 → "命令失败，退出码 1"（附报错文字）→ **程序没有崩**，"全部完成"照常出现。
3. 把 `"node -v"` 换成 `"npm -v"` 再跑一次，确认能拿到 npm 的版本号。
4. 运行 `npx tsc --noEmit`，确认没有任何输出。

## 小测

**1. 一条命令跑完，退出码是 0，说明什么？**

- A. 命令执行成功了
- B. 命令执行失败了
- C. 命令还在运行中
- D. 命令没有任何输出

::: details 点开核对答案

**答案：A（命令执行成功了）** —— 退出码 0 表示成功，非 0 表示失败，具体数字含义由程序自己定。

:::

**2. `promisify(exec)` 做了什么？**

- A. 把 Promise 函数还原成回调函数
- B. 把回调式函数包成 Promise 函数
- C. 把同步的函数变成多线程执行
- D. 把命令的输出直接打印到屏幕

::: details 点开核对答案

**答案：B（把回调式函数包成 Promise 函数）** —— promisify 吃进回调式函数，吐出返回 Promise 的函数，于是可以 await。

:::

**3. `stdout` 和 `stderr` 的区别是什么？**

- A. 中文输出与英文输出之分
- B. 屏幕输出与文件输出之分
- C. 正常输出与错误输出之分
- D. 同步输出与异步输出之分

::: details 点开核对答案

**答案：C（正常输出与错误输出之分）** —— stdout 装正常输出，stderr 装错误输出——只看 stdout 会漏掉失败原因。

:::

**4. `run_command` 跑的命令退出码是 2，工具该怎么反应？**

- A. 让整个 Agent 程序崩溃退出
- B. 忽略这次失败返回空的结果
- C. 自动换一条命令重新执行
- D. 把退出码和错误输出作为结果返回

::: details 点开核对答案

**答案：D（把退出码和错误输出作为结果返回）** —— 工具失败不该让 Agent 崩掉：把退出码与错误输出作为结果返回，模型自己决定下一步。

:::

**2. 不看正文：命令跑完的"三件套"——stdout、stderr、退出码，各自是什么？退出码几代表成功？**

::: details 显示答案

`stdout`：命令的正常输出；`stderr`：命令的错误输出；**退出码**：命令结束时报告给操作系统的数字，**0 = 成功，非 0 = 失败**。

::: info 安全要点：Agent 最危险的工具

`run_command` 什么命令都能跑——包括删文件、改系统配置。真实 Coding Agent 的做法：**跑命令前让用户确认**（你在 Kimi Code 里见过的权限弹窗就是它），危险命令直接拦截。给你的规则：永远不要把没读过的命令交给 `exec`。PatchPilot 阶段会专门写"危险命令拦截"的 Hook 插件。

:::

::: info 面试怎么考

"Node 里怎么执行 shell 命令？""exec 和 spawn 有什么区别？"是常见问题。后半问的答案先剧透一半：`exec` 把输出**全部攒到最后**一次性给你；要**边跑边看输出**（比如 npm install 的进度条）得用 `spawn` 加"流"——这正是第 7 课的主题。加分项还是那句设计："我的 run_command 把退出码和 stderr 作为工具结果返回给模型，而不是让 Agent 崩掉。"

:::
