# 第七课：使用 wayfinder 规划大型模糊项目

> 本文为站内全文版（已纳入搜索，随堂测为折叠核对）。随堂测可点击作答的交互版：[**打开讲义**](/blog/lessons/engineering-skills/lessons/0007-wayfinder.html){target="_blank"}

上一课的 `/diagnosing-bugs` 处理的是「东西坏了」的入口。这一课是入口场景系列的第二课，
处理另一种开局：**一个想法太大了，一个 agent session 装不下，而且从这里到目的地的路还看不见**。
直接 grill → to-spec 的主流程走不动它——spec 的前提是路已经清晰。
这种时候用 `/wayfinder`：先把「路」本身画出来，再谈施工。

::: info 主源推荐（Primary Source）

本课内容基于官方 skill 定义，建议精读原文：
[wayfinder/SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/wayfinder/SKILL.md)
（本地 `~/.agents/skills/wayfinder/SKILL.md`）。
建议完整读一遍原文，尤其是 Ticket Types 和 Fog of war 两节。

:::

## 1. wayfinder 是什么？

`/wayfinder` 把一大块模糊的工作绘制成 issue tracker 上的一张**共享地图（shared map）**，
然后一张一张地解决地图上的**决策票（decision ticket）**——
决议的结果是「一个决定」，而不是「一片要施工的功能切片」——直到通往目的地的路清晰为止。

原文有一个定位性原则：**plan, don't do（只规划，不施工）**。
地图画完的标志是「出发之前再没有什么需要决定的了」。如果你感到一股「别画了直接干吧」的冲动，
那恰恰是信号：你已经走到地图边缘，该交接给主流程（to-spec → to-tickets → implement）了。
个别工程可以在地图的 Notes 里声明例外（把施工也带进地图），但默认产出的是决策，不是交付物。

## 2. 地图：先命名目的地

绘制地图的第一个动作是**命名 destination（目的地）**——它塑造之后的每一张票。
目的地因工程而异：可能是要交接迭代的一份 spec、规划前必须锁定的一个决策、
或一次就地完成的变更（比如数据结构迁移）。地图本身与领域无关，工程、课程内容，任何符合这个形状的事都行。

地图是 tracker 上的一个 issue（标签 `wayfinder:map`），正文是整张地图的低分辨率视图，每个 session 开头加载一次：

- **Destination**：到达终点长什么样，一两行。每个 session 选票前先对准它。
- **Notes**：领域、每个 session 都该查阅的 skills、本工程的长期偏好。
- **Decisions so far**：索引——每张已关闭的票一行：一句话 gist + 链接。
- **Not yet specified**：战争迷雾区（见第 4 节）。
- **Out of scope**：被有意识地排除在目的地之外的工作。

::: info 地图是索引，不是仓库

一个决策只住在一个地方——它的票里。地图只 gist 和链接，从不复述细节。
**进行中的票也不列在地图上**：它们是打开的 child issue，靠查询找到。
引用任何地图或票时**用名字**（标题即链接），不要甩一串 `#42, #43`——名字一眼可读，编号墙不能。

:::

## 3. 决策票：四种类型与 frontier

每张票是地图的 child issue，正文就是一个 `## Question`——
**大小适配单个 100K token 的 agent session**（和第四课 ticket 适配上下文窗口是同一把尺子）。
每张票带一个 `wayfinder:<type>` 标签，四种类型：

| 类型 | 人在回路？ | 干什么 |
| --- | --- | --- |
| **research** | AFK | 读文档、第三方 API、本地知识库，把决策等待的事实挖出来。由 `/research` subagent 解决，可并行派发。 |
| **prototype** | HITL | 关键问题是「该长什么样 / 该怎么表现」时，用 `/prototype` 做个便宜粗糙的具体东西给大家 react。 |
| **grilling** | HITL | 对话，默认类型。总是配合 `/grilling` 和 `/domain-modeling`。 |
| **task** | HITL 或 AFK | 唯一「做」而非「决定」的类型：开通服务拿 API 凭证、迁移数据好让人看清形状。它存在的资格是**为某个决策解锁**，不是交付目的地。 |

HITL（human in the loop，人在回路）的票只能通过与真人的实时交流解决——
**agent 绝不能代替真人回答**（一个自问自答的 grilling agent 就破坏了这条）。

认领规则：**干活之前先把票 assign 给自己**，这样并发的其他 session 会跳过它——
assignee 就是认领标记。阻塞用 tracker 的**原生依赖关系**表达（能在 tracker 自己的 UI 上把前沿画出来）。
**frontier（前沿）** = 打开的、未被阻塞的、未被认领的票——已知的边缘。

## 4. 战争迷雾与范围之外

地图是**故意不完整的**：看不见的东西不要硬画。在活票之外是
[**fog of war（战争迷雾）**](https://github.com/mattpocock/skills/blob/main/skills/engineering/wayfinder/SKILL.md)——
你能感觉到会来、但还钉不死的决策和调查，因为它们挂在尚未解决的问题上。
每解决一张票，就清掉它前方的雾，把现在能具体化的部分「毕业」成新票——一次一张，直到路清晰、票耗尽。

::: info 雾还是票？一个判别式

标准是**你现在能否精确表述这个问题**——而不是能否回答它。
能精确表述（哪怕被阻塞、暂时动不了）→ 立票；表述不了 → 写进地图的 **Not yet specified**。
不要预先把雾切成票大小的片：雾比票粗，前沿推进到那里时，一片雾可能毕业成几张票，也可能一张都不用。

:::

**Out of scope（范围之外）**是另一回事：雾只会朝目的地方向聚集，目的地定了范围。
超出目的地的工作不是雾，不进 Not yet specified，而是进 Out of scope——
它**永不毕业**，只有重画目的地（作为全新工程）才会回来。
如果一张已存在的票被发现越过了目的地：**关掉它**（关闭的票就明确离开前沿了），
在 Out of scope 里留一行 gist + 原因 + 链接；它不进 Decisions so far——那里记录的是实际走过的路线，
而划范围不是路线上的一步。

## 5. 两种调用模式

**模式一：chart the map（绘制地图）**——用户带着一个模糊想法来：

1. **命名目的地**：先跑 `/grilling` + `/domain-modeling`，把这张地图要找到的东西钉死。目的地决定范围，所以最先定。
2. **广度优先画出前沿**：再 grill 一轮，这次是**广度优先**——铺满整个空间，而不是单点深挖，浮出所有开放的决策和现在就能迈的第一步。**如果没浮出任何雾**——路已经清晰、一个 session 装得下——那就不需要地图，停下来问用户想怎么走。
3. **建地图**（标签 `wayfinder:map`）：填好 Destination 和 Notes，Decisions-so-far 留空，雾写进 Not yet specified。
4. **立现在就能具体化的票**，然后**第二遍再连阻塞边**（票先有了 id 才能互相引用）。连线把它们分成前沿和被阻塞两组。
5. **派发 research subagent**：每张 research 票起一个 `/research` subagent 并行解决，成果落在一次性的 `research/<name>` 分支上，票里留上下文指针。
6. **停手**——绘制地图就是一个 session 的全部工作，它一张票都不亲手解决。

**模式二：work through the map（沿图推进）**——用户带着地图（URL 或编号）来，可以点名票，也可以让你挑：

1. 加载**地图**——低分辨率视图，不是每张票的正文。
2. 选票：用户点名就用点名的；否则取前沿第一张。**先认领**（assign 给自己）再干活。
3. 解决它——按需 zoom：相关票、已关闭票的正文随用随取；调用 Notes 里点名的 skills；拿不准就用 `/grilling` + `/domain-modeling`。
4. 记录结果：答案作为 **resolution comment（结案评论）**发出，**关闭** issue，在地图的 Decisions-so-far **追加一条上下文指针**（gist + 链接）。
5. 补新票（先建后连线）；把答案所清晰的雾毕业成票、从 Not yet specified 里划掉；发现某张票越过目的地就**判出范围**而不是顺手解决；答案推翻了地图其他部分就更新或删掉那些票。

::: info 铁律：一个 session 最多解决一张票

两种模式都适用（research 票除外）。这保证了每一步都有新鲜的上下文和明确的检查点。
用户可以让多张未阻塞的票并行跑在不同 session 里——所以要预期别的 session 正在同时编辑 tracker，先认领再干活。

:::

## 6. 实战场景：给妈妈音乐播放器加「歌单云同步」

你的「妈妈音乐播放器」MVP 已经跑通（第 5 课的实战项目）。现在来一个典型的模糊大想法：
**「想让歌单在多设备间同步」**。一个 session 装不下，路也看不见——正好套 wayfinder：

**1.** **命名目的地**：grill 一轮把目的地钉成「一份可以交接给 implement 的同步方案 spec」——
注意目的地不是「同步功能上线」，那是施工；这张地图只要走到「路清晰」。

**2.** **广度优先浮出决策**：自建后端还是用现成的 BaaS？匿名设备标识还是账号体系？
冲突怎么合并？离线期间的操作怎么排队？哪些能现在精确表述，哪些还是雾。

**3.** **建地图 + 立票**：「调研两个候选后端」立 research 票（派 subagent 并行查）；
「账号体系怎么选」立 grilling 票；「歌单合并策略的交互感觉」立 prototype 票；
「先开通候选服务的账号拿 API 凭证」立 task 票（它存在的资格是为后端选型解锁）。
第二遍连阻塞边：合并策略的讨论被后端选型阻塞。

**4.** **逐票推进**：之后的每个 session 只取前沿一张票，认领、解决、结案评论、
在 Decisions-so-far 留指针。后端选型定了，被阻塞的票解锁，雾里的「数据加密要不要做」
此刻能精确表述了——毕业成新票。直到有一天前沿清空：spec 所需的决定全部就绪，
交接给 `/to-spec` 主流程施工。

## 7. 小测验

**什么情况下该用 /wayfinder，而不是直接走 grill → to-spec 主流程？**

- A. 需求已经清晰，只差拆成可执行 ticket
- B. 想法大而模糊，路在一个 session 之外
- C. 线上报来一个时好时坏的难 bug
- D. 功能已经写完，要跨 session 交接上下文

::: details 点开核对答案

**答案：B（想法大而模糊，路在一个 session 之外）**

:::

**「Not yet specified（雾）」和正式 ticket 的分界线是什么？**

- A. 能否精确表述问题——能就立刻立票
- B. 能否立即回答问题——不能就进雾里
- C. 是否被其他票所阻塞——阻塞就进雾
- D. 是否在目的地范围内——在外就进雾

::: details 点开核对答案

**答案：A（能否精确表述问题——能就立刻立票）**

:::

**沿图推进时，一个 session 最多解决几张票？**

- A. 不限数量，上下文装得下就一直做
- B. 最多两张，前提是它们互不阻塞
- C. 只一张，research 票是例外可并行
- D. 最多三张，超过就要重画整个地图

::: details 点开核对答案

**答案：C（只一张，research 票是例外可并行）**

:::

**四种票类型里，唯一「做」而不是「决定」、靠为决策解锁来获得存在资格的是？**

- A. research：派 subagent 去查外部事实
- B. prototype：做个粗糙工件提高保真度
- C. grilling：用对话把模糊决策问清楚
- D. task：先开通服务拿到 API 的凭证

::: details 点开核对答案

**答案：D（task：先开通服务拿到 API 的凭证）**

:::

**【复习·第6课】诊断「锁屏后音乐停了」时，回路达到 red-capable 的标准是？**

- A. 断言用户的精确症状，能在其上变红
- B. 每次运行结果都一致，且秒级跑完
- C. 在模拟器上无人值守也可自动跑完
- D. 覆盖播放模块百分之八十以上代码

::: details 点开核对答案

**答案：A（断言用户的精确症状，能在其上变红）**

:::

**【复习·第2课】grilling 现在的提问制式是哪一种？**

- A. 一次只问一个问题，答完再问下个
- B. 每轮问完 frontier，问题带推荐答案
- C. 先出一份完整问卷让用户自己去填
- D. 只问是非判断题，降低用户作答负担

::: details 点开核对答案

**答案：B（每轮问完 frontier，问题带推荐答案）**

:::

## 8. 本课收获

- `/wayfinder` 处理「太大、太模糊、一个 session 装不下」的工程：把路绘成 tracker 上的共享地图，逐票解决决策，直到路清晰。
- 默认 plan, don't do：地图产出的是决策不是交付物；「想直接动手」的冲动就是该交接给主流程的信号。
- 地图是索引不是仓库：决策住在票里，地图只 gist + 链接；引用一律用名字，不用编号墙。
- 票分 research / prototype / grilling / task 四类；task 是唯一「做」的类型，资格是为决策解锁。
- 雾与票的判别式：能否**精确表述**问题（不是能否回答）；Out of scope 永不毕业，越界的票要关掉并记录。
- 铁律：一个 session 最多解决一张票（research 除外）；先认领再干活；结案要留 resolution comment 和 Decisions-so-far 指针。

## 9. 术语表

| 术语 | 解释 |
| --- | --- |
| destination | 目的地。这张地图要找到的东西——一份 spec、一个待锁的决策、一次就地变更。绘制地图的第一个动作，它决定范围、塑造每张票。 |
| shared map | 共享地图。tracker 上带 `wayfinder:map` 标签的单个 issue，是整项工程的权威 artifact；它是索引不是仓库。 |
| decision ticket | 决策票。地图的 child issue，正文是一个 `## Question`，决议结果是一个决定而非功能切片，大小适配单个 agent session。 |
| frontier | 前沿。打开的、未被阻塞的、未被认领的票——已知的边缘，下一个 session 从这里取票。 |
| claim | 认领。干活前先把票 assign 给驱动地图的人；assignee 就是认领标记，并发 session 会跳过已认领的票。 |
| fog of war | 战争迷雾。能感觉到会来、但还钉不死的决策与调查。地图故意不完整，雾随前沿推进逐渐「毕业」成票。 |
| Not yet specified | 尚未具体化。地图正文中记录雾的区块——范围内但还不足以立票的疑似问题，也是协作者看方向的指路牌。 |
| Out of scope | 范围之外。被有意识排除在本次目的地之外的工作；永不毕业，只有重画目的地（作为新工程）才会回来。 |
| HITL / AFK | 人在回路 / 离开键盘。HITL 的票只能通过与真人的实时交流解决，agent 不得代替真人作答；AFK 的票 agent 可独立完成。 |
| resolution comment | 结案评论。票被解决时把答案作为评论发出、关闭 issue，并在地图 Decisions-so-far 追加一条 gist + 链接的上下文指针。 |
| plan, don't do | 只规划不施工。wayfinder 的默认姿态：路清晰即地图完成，施工交接给 to-spec → implement 主流程。 |

## 10. 实战任务

找一个你自己真实「大而模糊」的工程——比如给妈妈音乐播放器加歌单云同步、给产品做国际化、
一次犹豫很久的数据迁移——任何「一个 session 装不下、路还看不见」的事。
调用 `/wayfinder`，亲手 chart 一张地图：

1. **命名目的地**：先用 grilling 把目的地钉死，一两行写清「到达长什么样」（多半是「一份可交接的 spec」）。
2. **广度优先浮出决策**：把整个空间扫一遍，能精确表述的立票，说不清的写进 Not yet specified，范围之外的写进 Out of scope。
3. **建地图**：有 issue tracker 就建带 `wayfinder:map` 标签的 issue；本地项目则用 local-markdown tracker——`.scratch/<effort>/map.md` + 每票一个 `issues/NN-<slug>.md`（`Type:` / `Status:` / `Blocked by:` 行）。
4. **立票 + 连线**：第一批票各标类型，第二遍再连阻塞边；research 票派 `/research` subagent 并行去查。
5. **停手**：这个 session 到此为止；另开新 session 从 frontier 取第一张票，走「认领 → 解决 → 结案评论 → 更新地图」的完整循环一次。

::: info 自检标准

- 地图上的 Destination 一两行能讲清「到达长什么样」，且范围之外的东西在 Out of scope 里，而不是混在雾里。
- 每张票是一个「问题」而不是功能切片，大小适配单个 session，四种类型标注正确。
- 阻塞边用 tracker 原生依赖（或本地的 `Blocked by:` 行）连好，frontier 一眼可查。
- 绘制地图的 session 没有亲手解决任何票；推进的 session 只解决了一张票，且留下了 resolution comment 和地图指针。

:::

完成后回来告诉我结果（贴出产出或描述过程），我会给你反馈。
