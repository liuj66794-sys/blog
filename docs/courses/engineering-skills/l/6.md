# 第六课：使用 diagnosing-bugs 诊断难 bug

## 1. diagnosing-bugs 是什么？

`/diagnosing-bugs` 是一套针对**难 bug 和性能回退**的诊断纪律。
触发信号就是你嘴里会说的那句话：「这个 bug 我复现不了」「这个东西时好时坏」「更新之后变慢了」。

它把诊断组织成六个阶段的循环：**建反馈回路 → 复现并最小化 → 提假设 → 探测 →
修复加回归测试 → 收尾复盘**。原文开宗明义：这是一条纪律，跳过任何阶段都需要明确的理由。

## 2. 第 1 阶段是灵魂：先建紧反馈回路

SKILL.md 原文说：**「This is the skill. Everything else is mechanical.」**
如果你有一个 tight feedback loop（紧反馈回路）——一个能在这个 bug 上变红、修好后变绿的 pass/fail 信号——
你迟早能找到原因：bisect、假设验证、插桩都只是消耗这个信号。
反之，**没有回路，盯着代码看多久都没用**。所以这一阶段要投入不成比例的精力：
激进一点、有创造力一点、拒绝放弃。

回路的核心品质是 [**red-capable（能变红）**](https://github.com/mattpocock/skills/blob/main/skills/engineering/diagnosing-bugs/SKILL.md)：
它必须真的驱动 bug 所在的代码路径，并且断言**用户描述的那个症状**——
不是「跑完没报错」，而是能抓住这一个具体的 bug。修好之后，同一条命令要变绿。

第 1 阶段的完成判据很硬：你能说出**一条已经跑过的命令**（贴出调用方式和输出），且它满足四条：

- **red-capable**：能在这个 bug 上变红、修好后变绿。
- **deterministic（确定）**：每次运行给出相同判定（flaky bug 则要求复现率足够高）。
- **fast**：秒级，不是分钟级。
- **agent-runnable**：agent 可以无人值守地跑；需要人操作时走 HITL 脚本。

::: info 反模式：回路不存在就去读代码

如果你发现自己在回路建好之前就去读代码、建理论——**停下来**。
原文明确说：直接跳到假设，正是这个 skill 要防止的那个失败。
没有 red-capable 的命令，就没有资格进入第 2 阶段。

:::

## 3. 十种建回路的方法

原文给出十种构造回路的方法，大致按这个顺序尝试：

| # | 方法 | 适用场景 |
| --- | --- | --- |
| 1 | 失败测试 | 在能触达 bug 的某个 seam 上写 unit / integration / e2e 测试。 |
| 2 | curl / HTTP 脚本 | 对跑着的 dev server 直接打请求，断言响应。 |
| 3 | CLI + 快照 | 喂一个 fixture 输入，把 stdout 和已知正确的快照 diff。 |
| 4 | headless 浏览器 | 用 Playwright / Puppeteer 驱动 UI，断言 DOM、console、网络。 |
| 5 | 重放 trace | 把真实请求 / 事件日志存盘，隔离地重放进代码路径。 |
| 6 | 一次性 harness | 搭一个最小子系统（mock 依赖），一次函数调用触发 bug 路径。 |
| 7 | property / fuzz | 「有时输出不对」型 bug：跑 1000 个随机输入找失败模式。 |
| 8 | bisect 台架 | bug 出现在两个已知状态之间：自动化「在状态 X 启动、检查、重复」，交给 `git bisect run`。 |
| 9 | 差分对比 | 同一输入分别跑旧版本和新版本（或两种配置），diff 输出。 |
| 10 | HITL 脚本（兜底） | 必须有人动手时，用 `scripts/hitl-loop.template.sh` 驱动人，回路依然是结构化的。 |

建好回路不算完，还要把它当产品一样**收紧**，问自己三个问题：

- 能更快吗？（缓存准备步骤、跳过无关初始化、缩小测试范围）
- 信号能更准吗？（断言具体症状，而不是「没崩溃」）
- 能更确定吗？（固定时间、给随机数种子、隔离文件系统、冻结网络）

30 秒还 flaky 的回路约等于没有回路；2 秒且确定的回路才是调试超能力。
对**非确定性 bug**，目标不是干净复现，而是**提高复现率**：
循环触发 100 次、并行、加压、收窄时间窗口。50% 的 flake 可以调试，1% 不行——持续提高复现率直到可调试为止。
实在建不出回路时，明确说出来，列出试过的方法，向用户要环境、要抓取物（HAR、日志、coredump）、或要加临时生产插桩的许可——不要在没有回路的情况下硬进假设阶段。

## 4. 第 2–4 阶段：复现、假设、探测

**第 2 阶段：复现 + 最小化。**跑回路，看着它变红，并确认三点：
失败模式就是用户描述的那个（修错 bug 等于没修）；多次运行可复现；症状已被精确记录。
然后把场景往小里砍：输入、调用方、配置、数据、步骤，**一次砍一个**，每砍一次重跑回路。
完成的标志是：剩下的每个元素都是 load-bearing（承重的）——再砍掉任何一个，回路就变绿。
最小复现既缩小了第 3 阶段的假设空间，也是第 5 阶段回归测试的毛坯。

**第 3 阶段：提假设。**验证任何假设之前，先生成
[**3–5 个排好序的假设**](https://github.com/mattpocock/skills/blob/main/skills/engineering/diagnosing-bugs/SKILL.md)——
只提一个假设会锚定在第一个貌似合理的想法上。每个假设必须 falsifiable（可证伪），用固定格式写出它的预测：

::: info 假设格式

「If &lt;X&gt; 是因，那么 &lt;改 Y&gt; 会让 bug 消失 / &lt;改 Z&gt; 会让它更严重。」

说不出预测，这个假设就是 vibe（感觉），丢掉或磨尖它。

:::

**排序后先给用户看**：用户常有领域知识能立刻重排（「我们昨天刚改过 #3」），
或知道哪些已经排除过。这是便宜的检查点，别跳过；用户不在就按你的排序继续，不阻塞。

**第 4 阶段：探测。**每个探针必须对应第 3 阶段的一个具体预测，
**一次只改一个变量**。工具偏好：调试器 / REPL 优先（一个断点胜过十条日志），
其次是在能区分假设的边界上打点日志，永远不要「到处打日志然后 grep」。
所有 debug 日志一律带唯一前缀，如 `[DEBUG-a4f2]`——收尾时一次 grep 就能删干净：
带前缀的日志会死，不带前缀的日志会活下来。

**性能回退走分支**：对 perf regression，日志通常是错的工具。
先测量——建立 baseline（计时台架、profiler、query plan），再 bisect。先测量，后修复。

## 5. 第 5–6 阶段：修复、回归测试与收尾

**第 5 阶段：修复 + 回归测试。**回归测试写在修复**之前**——但只在有
正确 seam（测试边界）的时候。正确的 seam 是指测试能像真实调用点那样触发 bug 模式；
如果唯一可用的 seam 太浅（bug 需要多个调用方串联，单测复现不了那条链），
在那里写回归测试只会带来虚假的信心。

::: info 没有正确 seam，本身就是发现

找不到正确的 seam，说明**代码架构在阻止这个 bug 被锁定**——这本身就是诊断成果。
记录下来，移交 `/improve-codebase-architecture`，不要硬写一个自欺的测试。

:::

有正确 seam 时的流程是第五课红绿循环的熟人：把最小复现变成该 seam 上的失败测试 →
看着它红 → 修复 → 看着它绿 → 最后用第 1 阶段的回路对**原始（未最小化的）场景**复跑一遍。

**第 6 阶段：收尾 + post-mortem（复盘）。**宣布完成之前，清单逐条过：

- 原始场景复跑，bug 不再出现（用第 1 阶段的回路）。
- 回归测试通过（或 seam 缺失已被记录）。
- 所有 `[DEBUG-...]` 插桩已删除（grep 前缀验证）。
- 一次性原型已删除（或移到明确标注的 debug 目录）。
- commit / PR 信息里写明**哪个假设最后被证实是对的**——让下一个调试者能学到。

最后问一句：「什么能阻止这个 bug 再次发生？」如果答案是架构层面的（没有好的测试 seam、调用方纠缠、隐藏耦合），
带着具体信息移交给 `/improve-codebase-architecture`。
建议在修复落地**之后**再提——此刻你掌握的信息比开工时多。

## 6. 实战场景：真机上「锁屏后音乐停了」

拿你自己的真实项目当例子。「妈妈音乐播放器」的 issue #5 是真机验证，
假设验证时发现：**锁屏后音乐停了**——模拟器上正常，真机上必现。六阶段怎么套：

**1.** **建回路**：真机问题没法用普通单测触达，用 adb 脚本或 HITL 脚本：
脚本启动播放 → 锁屏 → 等 60 秒 → 用 `adb shell dumpsys` 检查播放状态和前台服务是否存活。
断言是用户的精确症状「锁屏 60 秒后仍在播放」——现在它是红的。必须人工听声音确认的部分，走 HITL 脚本兜底。

**2.** **复现 + 最小化**：确认每次锁屏约 30 秒后停止，和用户描述一致；
逐步砍变量——换 Wi-Fi/流量、换音频文件、灭屏即停还是 30 秒后停——直到剩下的每个条件都是承重的。

**3.** **提假设**（排序后先给你看）：①前台服务没起来，锁屏后进程被冻结（「如果是这个原因，强制以前台服务启动后锁屏，音乐就不会停」）；
②厂商 ROM 的杀后台策略（「如果是这个原因，关掉电池优化后就不会停」）；
③BackgroundAudioManager 不支持包内音频路径，锁屏切换时播放中断（「如果是这个原因，换成网络音频 URL 就不会停」）。

**4.** **探测**：一次只验证一个假设；在播放状态切换处打 `[DEBUG-a4f2]` 前缀的日志，
用 `adb logcat` 抓取锁屏前后的服务生命周期。

**5.** **修复 + 回归测试**：假如证实是前台服务没起来，修复它。
然后找 seam：音频封装层有没有一个公共接口能断言「进入后台时前台服务已注册」？
有——回归测试写在那里；没有——「没有 seam」本身就是发现，记录并移交 `/improve-codebase-architecture`。

**6.** **收尾**：真机原始场景复跑一遍；`grep DEBUG-a4f2` 确认插桩清零；
commit 里写明「假设①被证实：前台服务未启动」，顺手关闭 issue #5 的这个子问题。

## 7. 小测验

**遇到一个难 bug（比如「真机锁屏后音乐停了」），按 diagnosing-bugs 的第一步是？**

- A. 通读播放模块代码，先建一个原因理论
- B. 建一个能在这个 bug 上变红的紧回路
- C. 在可疑的位置加一批日志再运行看看
- D. 凭经验直接修改最可疑的代码试一试

::: details 点开核对答案

**答案：B（建一个能在这个 bug 上变红的紧回路）**

:::

**tight loop 的四条判据中，哪一条最核心、缺了它其余都没意义？**

- A. red-capable——回路必须能在这个 bug 上变红
- B. deterministic——每次运行给出相同的判定
- C. fast——回路必须要在几秒钟内跑完一轮
- D. agent-runnable——agent 可以无人值守运行

::: details 点开核对答案

**答案：A（red-capable——回路必须能在这个 bug 上变红）**

:::

**关于 Phase 3 提假设，正确的做法是？**

- A. 先验证最可能的一个，不行再想下一个
- B. 生成 3–5 个假设后立即开始逐个测试
- C. 假设越具体越好，不必先给用户过目
- D. 生成 3–5 个可证伪假设，排序先给用户看

::: details 点开核对答案

**答案：D（生成 3–5 个可证伪假设，排序先给用户看）**

:::

**Phase 5 要写回归测试时，发现没有正确的 seam，该怎么办？**

- A. 退而求其次，在最浅的 seam 上写个测试
- B. 跳过回归测试，修完 bug 直接提交代码
- C. 这本身就是发现：记录并移交架构改进
- D. 先把代码重构成可测试的，再回头修复

::: details 点开核对答案

**答案：C（这本身就是发现：记录并移交架构改进）**

:::

**【复习·第4课】为什么每个 ticket 的大小要「适配单个上下文窗口」？**

- A. 让 issue tracker 上的数量显得更多
- B. 让全新 session 的 agent 能一次做完
- C. 让每个 ticket 只需要修改单个文件
- D. 让验收标准更容易浓缩成一句话

::: details 点开核对答案

**【复习·第5课】重构之后测试挂了，但代码行为根本没变——这是哪个反模式的识别信号？**

## 8. 本课收获

- `/diagnosing-bugs` 是难 bug 与性能回退的六阶段诊断循环：建回路 → 复现最小化 → 假设 → 探测 → 修复+回归测试 → 收尾复盘。
- 第 1 阶段是灵魂：没有 red-capable 的紧回路，读代码建理论就是这个 skill 要防止的失败。
- 回路的四条判据：red-capable、deterministic、fast、agent-runnable；建好后用「更快？更准？更确定？」持续收紧。
- 假设要 3–5 个、可证伪、排序后先给用户看；探测一次只改一个变量，debug 日志带 `[DEBUG-xxxx]` 前缀。
- 回归测试写在修复之前，但只在有正确 seam 时；没有 seam 本身就是发现，移交架构改进。

## 9. 术语表

| 术语 | 解释 |
| --- | --- |
| tight feedback loop | 紧反馈回路。一个快速、确定、能在 bug 上变红的 pass/fail 信号，是整个诊断的地基。 |
| red-capable | 能变红。回路真的驱动 bug 代码路径并断言用户的精确症状，能在这个 bug 上变红、修好后变绿。 |
| deterministic | 确定。同一回路每次运行给出相同判定；flaky bug 则要求复现率被提高到可调试的水平。 |
| agent-runnable | agent 可运行。回路可以无人值守执行；必须有人操作时通过 HITL 脚本保持结构化。 |
| seam | 测试边界（第五课）。在其上观察行为的公共接口；回归测试只有写在正确的 seam 上才有意义。 |
| load-bearing | 承重的。最小复现里剩下的每个元素都是承重的——再砍掉任何一个，回路就变绿。 |
| falsifiable hypothesis | 可证伪假设。能写出明确预测的假设：「如果 X 是因，那么改 Y 会让 bug 消失」；说不出预测的就是 vibe。 |
| bisect | 二分定位。在两个已知状态（commit、版本、数据集）之间自动二分，找出引入 bug 的那一点。 |
| differential loop | 差分回路。同一输入分别跑新旧两个版本（或两种配置），diff 输出找差异。 |
| HITL | human-in-the-loop，人在回路。必须人工操作时用 `scripts/hitl-loop.template.sh` 驱动人，保持回路结构化。 |
| regression test | 回归测试。把最小复现固化成测试，锁定这个 bug 不再复发；写在修复之前。 |
| post-mortem | 复盘。修复后追问「什么能阻止它再次发生」，架构性答案移交 `/improve-codebase-architecture`。 |

## 10. 实战任务

拿一个**真实的难 bug** 走完六阶段。首选你自己项目里的那个：
「妈妈音乐播放器」issue #5 的真机问题（锁屏后音乐停了，或验证中实际发现的任何一个）；
也可以另选一个你一直复现不了、时好时坏的 bug。调用 `/diagnosing-bugs`，亲手走一遍：

1. **建回路**：用十种方法里最合适的一种（真机问题多半是 adb 脚本或 HITL 脚本），建一个 red-capable 的回路，**真的跑一次**，把命令和输出留下来。
2. **复现 + 最小化**：确认失败模式就是用户描述的那个；一次砍一个变量，直到剩下的每个元素都是承重的。
3. **提假设**：写出 3–5 个可证伪假设（「If X 是因，那么改 Y 会……」格式），排好序先给自己/合作者过目，再开始验证。
4. **探测 + 修复**：一次只改一个变量；debug 日志全带 `[DEBUG-xxxx]` 前缀；把最小复现变成正确 seam 上的回归测试——或者记录下「没有正确 seam」这个发现。
5. **收尾**：原始场景复跑、grep 清掉插桩、commit 里写明哪个假设被证实是对的。

::: info 自检标准

- 你能说出一项**已经跑过的** red-capable 命令（脚本路径、测试调用或 curl），并贴得出它的输出。
- 你写出过 3–5 个可证伪假设，每个都带「改 Y 会怎样」的预测。
- 所有 debug 日志都带 `[DEBUG-xxxx]` 前缀，且收尾时已经 grep 清理干净。
- 回归测试落在正确的 seam 上——或者你明确记录了 seam 缺失这个发现。

:::
