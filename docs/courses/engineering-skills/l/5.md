# 第五课：使用 implement 完成实现

> 本文为站内全文版（已纳入搜索，随堂测为折叠核对）。随堂测可点击作答的交互版：[**打开讲义**](/blog/lessons/engineering-skills/lessons/0005-implement.html){target="_blank"}

上一课你用 `/to-tickets` 把 spec 拆成了一组带阻塞边的 ticket，发布到了 issue tracker。
这一课学习主线的最后一环：怎么用 `/implement` 按 frontier（前沿）逐个领取 ticket，
把代码写出来、测好、审查完、提交。

::: info 主源推荐（Primary Source）

本课内容基于官方 skill 定义，建议精读原文：
[implement/SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/implement/SKILL.md)、
[tdd/SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/tdd/SKILL.md)、
[code-review/SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/code-review/SKILL.md)
（本地 `~/.agents/skills/` 下同名目录）。
tdd 目录下还有 `tests.md`（好测试示例）和 `mocking.md`（mock 准则）两份延伸阅读。

:::

## 1. implement 是什么？

`/implement` 根据 spec 或 ticket 完成实现工作。它是主流程 idea → ship 的“ship”端：
输入是 tracker 上 agent-ready 的 ticket，输出是提交到当前分支的、经过审查的代码。

有意思的是，`/implement` 的 SKILL.md 本身非常短——它只有五条规则。
它是一个**编排者**：真正的深度在它调用的两个 skill 里——
`/tdd`（怎么写实现）和 `/code-review`（怎么收尾）。
所以这一课的大部分内容，是学这两个被驱动的 skill。

## 2. implement 的五条规则

SKILL.md 全文就这么多，但每条都有讲究：

1. **实现 spec/ticket 描述的工作**——不多做，也不少做。范围由 ticket 的验收标准界定。
2. **尽可能用 [`/tdd`](https://github.com/mattpocock/skills/blob/main/skills/engineering/tdd/SKILL.md)，在预先约定的 seam（测试边界）上写测试**——seam 要和用户确认过才能用。
3. **验证节奏**：经常跑类型检查、经常跑单个测试文件，**完整测试套件只在最后跑一次**。这是为速度设计的：全量套件慢，红灯阶段跑单文件就够了。
4. **完成后跑 `/code-review`**——审查通过前不算完。
5. **提交到当前分支**——工作以 commit 收尾，ticket 才能标记完成、frontier 才能向前推进。

## 3. 前置条件

- 项目已运行过 `/setup-matt-pocock-skills`（issue tracker、triage labels、CONTEXT.md/ADR 就绪）。
- ticket 已在 tracker 上，且你领取的这个 ticket 位于 **frontier** 上——它的所有阻塞项都已完成。
- **每个 ticket 开一个新 session**。这是第一课 context hygiene（上下文卫生）的下半句：
grill → to-spec → to-tickets 共享一个上下文，而每个 `/implement` 从 ticket 出发、全新开始，
避免前几阶段的讨论噪音污染实现。

## 4. 一个 ticket 的生命周期

**1.** **领取**：从 frontier 上取一个 ticket，读它的验收标准和 spec 上下文。

**2.** **约定 seam**：写任何测试之前，先和用户确认“公共接口是什么、测哪些 seam”。

**3.** **red → green 循环**：一个失败测试 → 刚好够通过的实现 → 下一个测试。期间勤跑类型检查和单测试文件。

**4.** **全量验证**：所有切片完成后，跑一次完整测试套件。

**5.** **审查**：跑 `/code-review`，处理 Standards 和 Spec 两个轴的发现。

**6.** **提交**：commit 到当前分支，关闭 ticket，frontier 向前推进。

## 5. tdd 深入：什么是好测试

`/tdd` 的核心主张：**测试通过公共接口验证行为，而不是验证实现细节**。
实现可以整个重写，测试不应该跟着改。一个好测试读起来像规格说明——
“用户可以用有效购物车结账”直接告诉你系统具备什么能力——并且能在重构中幸存，
因为它不关心内部结构。

探索代码库时，`/tdd` 要求先读 `CONTEXT.md`（如果存在），
让测试命名和接口词汇与项目的领域语言一致，并尊重相关区域的 ADR——
这正是第二课 grilling 阶段维护的那些文档在实现期发挥作用的地方。

## 6. Seams：只在预先约定的边界写测试

[**seam（测试边界）**](https://github.com/mattpocock/skills/blob/main/skills/engineering/tdd/SKILL.md)是你在其上观察行为的公共边界——不需要把手伸进内部就能验证结果的接口。
测试只活在 seam 上，绝不针对内部实现。

::: info 铁律：先约定，后测试

写任何测试之前，把要测的 seam 写下来并和用户确认。**没有任何测试写在未确认的 seam 上**。
你不可能测所有东西——事先约定 seam，是让测试投入落在关键路径和复杂逻辑上、而不是每个边缘案例上的方法。

标准问法：*“公共接口是什么？我们应该测哪些 seam？”*

:::

回看第三课：to-spec 的模板里就要求声明 seams。所以到 implement 阶段，seam 通常已经不是新问题，
而是从 spec 继承下来、再和用户确认一遍。

## 7. tdd 的三个反模式

- **implementation-coupled（耦合实现）**：mock 内部协作者、测私有方法、
或绕开接口走旁路验证（比如直接查数据库而不是调接口）。
*识别信号*：重构后测试挂了，但行为根本没变。
- **tautological（同义反复）**：断言用和代码相同的方式重算期望值，
比如 `expect(add(a, b)).toBe(a + b)`——测试在构造上必然通过，永远不可能和代码产生分歧。
期望值必须来自**独立的真相来源**：已知正确的字面量、手工算过的例子、spec。
- **horizontal slicing（水平切片）**：先写完全部测试，再写全部实现。
批量写出来的测试验证的是*想象中*的行为——你测的是事物的“形状”而不是面向用户的行为，
而且在理解实现之前就锁定了测试结构。正确做法是**垂直切片**：
一个测试 → 一个实现 → 重复，每个测试都是一颗 tracer bullet（曳光弹），根据上一轮学到的东西调整方向。

## 8. 循环的三条规则

1. **Red before green（先红后绿）**：先写失败的测试，再写刚好够让它通过的代码。
不预判未来的测试，不加投机性的功能。
2. **One slice at a time（一次一片）**：每个循环只处理一个 seam、一个测试、一个最小实现。
3. **重构不属于循环**：red → green 实现循环里不做重构；重构属于后面的审查阶段
（由 `/code-review` 驱动）。循环中保持最小步进，清理留给收尾。

## 9. code-review 深入：双轴审查

实现完成后，`/code-review` 沿着[**两个互相独立的轴**](https://github.com/mattpocock/skills/blob/main/skills/engineering/code-review/SKILL.md)审查
某个 fixed point（固定点，如 commit、分支、tag）以来的 diff：

| 轴 | 审查什么 |
| --- | --- |
| **Standards（规范）** | 代码是否符合本仓库成文的编码规范（如 CODING_STANDARDS.md、CONTRIBUTING.md），外加一套固定的 Fowler code smell（代码坏味道）基线。 |
| **Spec（需求）** | 代码是否忠实实现了原始 issue/PRD/spec：有没有漏做的需求、多做的行为（scope creep，范围蔓延）、做错的实现。 |

两个轴由**并行的 sub-agent（子代理）**分别执行，互不污染上下文，
最后由 skill 汇总成 `## Standards` 和 `## Spec` 两份报告——
刻意**不合并、不重排**发现。

### 为什么要两个轴

因为一次改动可能过一个轴、挂另一个轴：

- 代码完全符合规范，但实现了错误的东西 → Standards 过，Spec 挂。
- 代码完全按需求实现，但破坏了项目约定 → Spec 过，Standards 挂。

分开报告，防止一个轴的好成绩掩盖另一个轴的问题。

### smell 基线的两条约束

- **仓库规范优先**：成文的仓库标准永远赢；如果仓库明确认可某种基线会标记的写法，就抑制该 smell。
- **永远是判断题**：每个 smell 是带标签的启发式（“可能的 Feature Envy”），不是硬性违规；
工具（linter、格式化器）已经管的一律跳过。

基线包含 12 种 Fowler 坏味道：Mysterious Name、Duplicated Code、Feature Envy、Data Clumps、
Primitive Obsession、Repeated Switches、Shotgun Surgery、Divergent Change、
Speculative Generality、Message Chains、Middle Man、Refused Bequest。
每种都以“是什么 → 怎么修”的形式给出，详见
[配套参考页](/blog/lessons/engineering-skills/reference/implement-reference.html)。

## 10. 小例子：实现“部分退款”的第一个 ticket

沿用前几课的例子。假设 `/to-tickets` 产出的第一个 ticket 是：

::: info Ticket #12：端到端打通“发起部分退款”最小流程

Blocked by: None（在 frontier 上）。

验收标准：用户可以对已支付订单发起一笔小于订单总额的退款；退款金额超过剩余可退余额时被拒绝；
成功后订单显示可退余额减少。

:::

`/implement` 的过程：

1. **约定 seam**。和用户确认：公共接口是 `POST /orders/:id/refunds`，
测试就打在这个 HTTP 边界上——不直接 new 内部的 RefundService，也不查数据库验证。
2. **Red**：写第一个测试“对已支付订单发起部分退款，返回 201 且余额减少”——红灯，接口还不存在。
3. **Green**：写刚好够通过的最小实现：路由 + 校验 + 更新余额。期间反复跑这一个测试文件和类型检查。
4. **下一个 red**：“退款金额超过可退余额，返回 422”——再加刚好够的校验逻辑。一个切片接着一个切片。
5. **全量验证**：所有验收标准变绿后，跑一次完整测试套件。
6. **双轴审查**：跑 `/code-review`。
Standards 轴报告：“可能的 Primitive Obsession——金额用裸 number 传来传去，建议引入 Money 类型”（判断题，和用户讨论后决定记录为后续 prefactor）。
Spec 轴报告：“spec 要求‘退款必须填写原因’，当前实现缺失”——这是硬性遗漏，补上。
7. **提交**：commit，ticket #12 关闭，frontier 推进到下一个 ticket。

## 11. 小测验

**/implement 领取 ticket 后、写任何测试之前，必须先做什么？**

- A. 先把 ticket 涉及的所有测试一次性写出来
- B. 和用户确认公共接口和要测的 seam
- C. 先重构相关代码，让实现更容易
- D. 先跑一遍完整测试套件确认全绿

::: details 点开核对答案

**答案：B（和用户确认公共接口和要测的 seam）**

:::

**下面哪个测试是 tautological（同义反复）测试？**

- A. 调用 HTTP 接口创建退款，断言响应码是 201
- B. 用 spec 里手工算过的例子断言退款余额
- C. `expect(add(a, b)).toBe(a + b)`
- D. 断言非法输入被拒绝并返回固定错误码 422

::: details 点开核对答案

**答案：C（expect(add(a, b)).toBe(a + b)）**

:::

**关于 red → green 循环中的重构，正确的是？**

- A. 每次绿灯之后立即重构一遍
- B. 红灯阶段顺便重构相关代码
- C. 所有测试写完后统一重构
- D. 循环中不做重构，留给审查阶段

::: details 点开核对答案

**答案：D（循环中不做重构，留给审查阶段）**

:::

**一次改动完全符合仓库编码规范，但实现的功能和 spec 要求的不一样。/code-review 的结果会是？**

- A. Standards 通过，Spec 失败
- B. Standards 失败，Spec 通过
- C. 两个轴都失败
- D. 两个轴都通过

::: details 点开核对答案

**答案：A（Standards 通过，Spec 失败）**

:::

**【复习·第3课】/to-spec 产出的 spec 中，为什么不写具体文件路径和代码片段？**

- A. 文件路径和代码很快会过时，spec 会跟着失真
- B. 文件路径属于仓库内部信息，不宜写进公开 issue
- C. spec 面向非技术读者，不应出现任何技术细节
- D. 代码一律只能写进 ADR，spec 里不允许例外

::: details 点开核对答案

**答案：A（文件路径和代码很快会过时，spec 会跟着失真）**

:::

**【复习·第4课】实现阶段说的 frontier（前沿）指的是什么？**

- A. 阻塞其他 ticket 最多、应优先安排的 ticket
- B. 所有阻塞项已完成、此刻可以开工的 ticket
- C. 还没有填写 Blocked by 字段的草稿 ticket
- D. 已经实现完毕、正在等待审查的 ticket

::: details 点开核对答案

**答案：B（所有阻塞项已完成、此刻可以开工的 ticket）**

:::

## 12. 本课收获

- `/implement` 是编排者：按 frontier 领 ticket，内部驱动 `/tdd`，收尾跑 `/code-review`，最后 commit。
- 每个 ticket 开新 session 实现——这是 context hygiene 的下半句。
- 测试只写在预先和用户确认的 seam 上，通过公共接口验证行为。
- 三个反模式：implementation-coupled、tautological、horizontal slicing。
- red → green 一次一片，重构不属于循环，留给审查阶段。
- 验证节奏：勤跑类型检查和单测试文件，完整套件只在最后跑一次。
- `/code-review` 双轴独立报告：Standards（仓库规范 + Fowler smell 基线）与 Spec（需求符合度），互不掩盖。

## 13. 术语表

| 术语 | 解释 |
| --- | --- |
| seam | 测试边界。在其上观察行为的公共接口，测试只写在这里，不触碰内部实现。 |
| red → green loop | 红绿循环。先写失败测试（红），再写刚好够通过的实现（绿），逐片推进。 |
| implementation-coupled | 耦合实现的测试。mock 内部协作者、测私有方法或走旁路验证；重构时它会误报。 |
| tautological test | 同义反复测试。断言用和代码相同的方式重算期望值，构造上必然通过，永远无法发现错误。 |
| horizontal slicing | 水平切片。先写完全部测试再写全部实现，验证的是想象中的行为；应对做法是垂直切片逐轮推进。 |
| fixed point | 固定点。code-review 审查 diff 时的比较基准：commit SHA、分支名、tag 等。 |
| smell baseline | 坏味道基线。code-review 内置的 12 种 Fowler code smell，即使仓库没有成文规范也适用，但每条都是判断题。 |
| scope creep | 范围蔓延。diff 里出现了 spec 没有要求的行为，是 Spec 轴的发现之一。 |
| sub-agent | 子代理。code-review 为两个审查轴各启动一个并行子代理，避免互相污染上下文。 |
| frontier | 前沿（第四课）。所有阻塞项均已完成、此刻可以开工的 ticket 集合；implement 从这里领取工作。 |

## 14. 实战任务

在你自己的真实项目里完成下面的任务：领取上一课 `/to-tickets` 拆出的第一个 ticket
（Blocked by 为 None、就在 frontier 上的那个），用 `/implement` 走完 red → green → code-review 全流程。

1. **领取 ticket**：确认它在 frontier 上，通读验收标准和关联的 spec，然后开一个全新 session 启动 `/implement`。
2. **约定 seam**：写任何测试之前，先把公共接口和要测的 seam 写下来并确认。
3. **red → green 逐片推进**：一次一个失败测试、一份刚好够通过的实现；期间勤跑类型检查和单测试文件。
4. **全量验证 + 双轴审查**：跑一次完整测试套件，然后跑 `/code-review`，处理 Standards 和 Spec 两个轴的发现。
5. **提交收尾**：commit 到当前分支，关闭 ticket，frontier 向前推进。

::: info 自检标准

- 所有测试都只写在事先约定的 seam 上，没有任何测试触碰内部实现。
- 每个测试都先红后绿——你见过它失败的样子，而不是批量写完后才第一次运行。
- 完整测试套件只在收尾时跑，循环期间用的是类型检查和单测试文件。
- `/code-review` 的 Standards 与 Spec 两份报告均已处理，没有未回应的发现。

:::

或跨 session 的 `/handoff`。也可以直接实战：拿一个真实想法，从 grill 一路走到 implement。
