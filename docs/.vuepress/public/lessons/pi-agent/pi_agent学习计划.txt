那就把这条路线明确成：

> **以一个自己的 Coding Agent 为主项目，用 Pi 学习 Agent Harness 的最小实现，再逐步补齐上下文、恢复、评测和可观测性。**

不要先把 LangChain、MCP、多 Agent、向量数据库全部学一遍。这个岗位真正需要的不是“会调用 Agent 框架”，而是能解释并解决：

- Agent 为什么选择了错误文件
- 为什么工具调用失败后无法恢复
- 为什么长任务逐渐偏离目标
- 如何判断一次修改是否真的成功
- 如何通过 trace 和评测持续改进系统

## 一、技术路线选择

### 主语言：TypeScript

第一阶段建议用 TypeScript，而不是同时学四门语言。原因不是 TypeScript 更适合所有 Agent，而是：

1. Pi 本身就是 TypeScript 项目。
2. 你要重点学习 Node.js 中的进程、流、文件系统、异步取消、CLI 和工具执行。
3. 这些能力与 Coding Agent 的工程实现高度重合。

Pi 官方目前将项目拆为几个相对清晰的部分：

- `pi-ai`：不同模型提供商的统一接口
- `pi-agent-core`：Agent Loop、工具调用和状态管理
- `pi-coding-agent`：面向代码任务的 CLI
- `pi-tui`：终端界面

Pi 的定位就是一个最小化 Agent Harness，通过 TypeScript Extension、Skill、Prompt Template 等方式扩展，而且刻意不默认加入 plan mode 和 sub-agent，这反而很适合学习这些能力应该如何实现。

Python可以作为第二语言，主要用于：

- 评测数据处理
- trace 分析
- 实验脚本
- 可视化
- 使用部分 AI/ML 库

## 二、你的核心项目

建议暂时不要做“万能私人助理”，而是做一个边界明确的项目：

# PatchPilot：本地代码仓库修复 Agent

输入：

```text
一个本地 Git 仓库
一段 issue / 开发需求
允许执行的测试命令
```

输出：

```text
代码修改
Git diff
测试结果
执行 trace
成功或失败原因
```

它至少支持：

```text
list_files
read_file
search_code
write_file / apply_patch
run_command
git_diff
```

Agent Loop 的最小逻辑：

```text
接收任务
  ↓
构造上下文
  ↓
调用模型
  ↓
模型选择工具
  ↓
执行工具并返回结果
  ↓
继续调用模型
  ↓
运行测试和检查 diff
  ↓
完成或失败
```

这个项目几乎能覆盖截图中岗位要求的主要部分：工具调用、代码库上下文、长任务、状态恢复、trace、评测和失败分析。

## 三、四个月学习计划

### 第 1 月：做出最小可运行 Agent

| 周次    | 学习重点                                        | 交付物                   |
| ------- | ----------------------------------------------- | ------------------------ |
| 第 1 周 | TypeScript、Node.js 异步、文件系统、Git、Vitest | 一个可以调用模型的 CLI   |
| 第 2 周 | Tool Calling、参数校验、Agent Loop              | 支持计算器和文件读取工具 |
| 第 3 周 | Shell、搜索、文件修改、超时和取消               | 能在测试仓库中修改代码   |
| 第 4 周 | Git diff、测试验证、基础日志                    | PatchPilot v0.1          |

这一阶段不要加入记忆、规划和多 Agent。

你真正需要理解的是：

```ts
while (!finished && step < maxSteps) {
  const response = await model.generate(context, tools);

  if (response.toolCalls.length === 0) {
    return response.text;
  }

  for (const call of response.toolCalls) {
    const result = await toolExecutor.execute(call);
    context.push(call, result);
  }
}
```

然后逐步研究这些问题：

- 模型一次返回多个工具调用怎么办？
- 工具参数不合法怎么办？
- Shell 命令超时怎么办？
- 用户中途取消怎么办？
- 工具输出太长怎么办？
- 模型不断重复同一个操作怎么办？
- 如何定义真正的“任务完成”？

### 第 2 月：代码库上下文工程

第二个月不追求增加更多工具，而是解决“给模型什么信息”。

实现：

- `.gitignore` 过滤
- 目录树生成
- 文件大小限制
- 代码搜索
- 最近修改文件
- `AGENTS.md` 项目说明
- token budget
- 工具输出截断
- 对话压缩
- repository map

建议设计一个统一的上下文预算：

```ts
interface ContextBudget {
  systemPromptTokens: number;
  projectInstructionTokens: number;
  fileContentTokens: number;
  historyTokens: number;
  toolResultTokens: number;
  reservedOutputTokens: number;
}
```

重点实验：

> 同一个任务，分别使用“整个仓库”“搜索后选文件”“目录树加相关文件”三种上下文策略，比较成功率、token 消耗和错误修改数量。

这类实验比单纯做一个漂亮 UI 更接近岗位要求。

### 第 3 月：可靠性与恢复机制

加入任务状态机：

```text
CREATED
ANALYZING
IMPLEMENTING
TESTING
RECOVERING
COMPLETED
FAILED
CANCELLED
```

实现：

- 最大步数
- token 和费用预算
- 命令超时
- AbortSignal
- 自动重试
- checkpoint
- session 持久化
- 重启后恢复
- 重复操作检测
- 测试失败后的修复循环
- Git worktree 或容器隔离
- 危险命令确认

尤其要区分：

```text
工具调用失败
工具调用成功但结果为空
命令返回非零退出码
测试失败
Agent 推理方向错误
模型 API 暂时错误
上下文超限
```

不要把它们都归类成一个 `error`。

真实 Agent 工程中，错误语义本身就是重要问题。例如 Pi 的公开 issue 中就出现过 `grep` 返回 1 代表“没有匹配”，却被系统记录为工具错误，最终影响 trace 和评测统计的情况。

### 第 4 月：Trace、评测和实验系统

先使用简单的 JSONL：

```json
{
  "runId": "run-001",
  "step": 4,
  "event": "tool_result",
  "tool": "run_command",
  "durationMs": 1420,
  "isError": false,
  "inputTokens": 2531,
  "outputTokens": 318
}
```

每个 Agent Run 至少记录：

- 用户任务
- 模型和参数
- 每一步上下文
- 工具输入与输出
- 文件修改
- 测试结果
- token 数
- 延迟
- 费用
- 最终状态
- 人工失败标签

然后建立自己的小型评测集，例如 30 个任务：

| 类型       | 示例                     |
| ---------- | ------------------------ |
| 定位错误   | 找出一个错误条件判断     |
| 小功能     | 增加一个 CLI 参数        |
| 测试修复   | 修复 failing test        |
| 重构       | 提取重复函数             |
| 跨文件修改 | 同时修改类型、实现和测试 |
| 恢复任务   | 第一次修改失败后继续修复 |

指标包括：

```text
任务成功率
测试通过率
代码能否编译
无关文件修改数量
平均工具调用次数
平均 token 消耗
平均完成时间
失败恢复率
重复操作率
```

等系统结构稳定后，再接入 OpenTelemetry。OpenTelemetry 中一个操作通常对应一个 span，多个相关 span 组成 trace，可以记录时间、状态、属性和事件，适合表达一次 Agent 任务中的模型调用、工具调用和测试执行。

## 四、如何学习 Pi，而不是只会使用 Pi

建议按四层进行。

### 第一层：把 Pi 当工具使用

用 Pi 完成十个真实小任务：

- 修改自己的课程项目
- 加一个单元测试
- 修复一个 Bug
- 重构一个模块
- 阅读陌生仓库

每次都记录：

```text
它第一次选了哪些文件
调用了哪些工具
在哪一步偏离
你什么时候需要干预
最后是否真的通过测试
```

### 第二层：为 Pi 写扩展

先写三个扩展：

1. `task-budget`：限制步数和费用
2. `dangerous-command-guard`：拦截危险命令
3. `trace-exporter`：导出结构化 trace

这样你会接触：

- 工具注册
- 生命周期 Hook
- Session
- Agent 事件
- TUI 输出
- 错误处理

### 第三层：自己实现 Mini Pi

不要直接复制源码。

先仅凭自己的理解实现：

```text
模型适配器
Agent Loop
工具注册表
工具执行器
Session
JSONL Trace
CLI
```

控制在两三千行以内。

完成后再对照 Pi 源码，观察：

- 你的 abstraction 哪里过度设计
- Pi 如何处理 streaming
- tool call 和 tool result 如何表示
- session 如何持久化
- cancellation 如何传递
- context compaction 在什么位置发生
- provider 差异如何被隔离

### 第四层：阅读并贡献源码

推荐阅读顺序：

```text
pi-ai
  ↓
pi-agent-core
  ↓
coding-agent 中的 tools
  ↓
agent session
  ↓
context / compaction
  ↓
extensions
  ↓
TUI
```

不要一开始就从终端 UI 阅读，那部分代码量较大，而且不是 Agent 核心。

## 五、什么时候学习 MCP 和多 Agent

### MCP：第三个月之后

先自己实现普通工具调用，再学习 MCP。否则你只会配置 MCP Server，却不理解工具系统本身。

MCP 当前的核心结构是：

```text
Host
  └── Client
        └── Server
```

服务端可以提供：

```text
Resources
Prompts
Tools
```

底层使用 JSON-RPC，并包含能力协商、进度、取消、日志和错误报告等机制。官方规范也特别强调了任意数据访问和代码执行带来的安全问题。

你的实践任务可以是：

> 把 PatchPilot 的代码搜索工具封装成一个 MCP Server，再让自己的 Agent 和 Pi 分别调用它。

这样你才能真正理解 MCP 解决了什么问题，又没有解决什么问题。

### 多 Agent：第四个月之后

不要因为“多 Agent 看起来更高级”就过早加入。

只有当你能说明下面的问题时才值得做：

```text
为什么一个 Agent 不够？
子 Agent 得到了什么独立上下文？
任务如何拆分？
结果如何合并？
多个 Agent 如何避免重复工作？
并行执行是否真的降低了时间？
额外 token 成本是否值得？
```

可以从两个子 Agent 开始：

- `explorer`：只读，负责定位代码
- `coder`：根据 explorer 的结果修改代码

不要一开始就做五六个角色互相聊天。

## 六、之后再研究 Kimi Code

完成自己的最小 Agent 和 Pi 源码学习后，可以把 Kimi Code 作为第二个大型样本。

当前官方开源版本包含代码读写、Shell、文件搜索、MCP、sub-agent、生命周期 Hook 和编辑器协议集成等能力，并提供完整的 TypeScript 开发和测试流程。

可以做一份对比分析：

| 维度         | 你的 Agent | Pi   | Kimi Code |

| Context 管理 |            |      |           |

这份分析本身就能成为很好的技术文章或面试材料。

## 八、你现在最应该做的第一步

本周只完成下面这个闭环：

```text
用户输入一个任务
→ 模型调用 read_file
→ 模型调用 apply_patch
→ 系统执行测试
→ 输出 Git diff
→ 将全过程保存成 JSONL
```

准备五个非常简单、答案明确的测试任务。每修改一次 Agent，都重新跑这五个任务。

从第一周就建立评测意识，而不是等 Agent“开发完成”后再评测。到大三时，一个有真实代码、实验数据、失败案例、技术文章和开源贡献的项目，会比“熟悉十几个 AI 框架”更有说服力。
