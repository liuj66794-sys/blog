to-spec 模板与流程参考

把 grilling 的结果合成为一份 PRD/spec，发布到 issue tracker（问题追踪系统）。

来源：mattpocock/skills · to-spec/SKILL.md（本地 ~/.agents/skills/to-spec/SKILL.md）

一、什么时候用

  • 已经完成 /grill-with-docs 或 /grill-me，对话足够清楚。
  • 需要一个正式的 PRD/spec 文档作为后续工作的依据。
  • 准备把 spec 发布到 issue tracker，供 /to-tickets 拆分。

二、前置条件

/to-spec 假设项目已经运行过 /setup-matt-pocock-skills， 因此知道 issue tracker 在哪里、triage labels（分类标签）怎么叫。 如果没有设置，agent 会提示你先运行 setup。

三、流程

1

探索代码库（如果还没做）：理解当前状态，使用 CONTEXT.md 的词汇，尊重 ADR。

2

草拟 seams（测试边界）：确定测试接口。优先复用现有 seams，用最高层级的 seam。理想数量是 1。

3

和用户确认 seams：确保测试边界符合预期。

4

按模板写 spec：合成当前对话，不再 interview。

5

发布到 issue tracker，应用 ready-for-agent 标签。

四、Spec 模板

## Problem Statement

用户视角的问题描述。

## Solution

用户视角的解决方案。

## User Stories

1. As an <actor>, I want a <feature>, so that <benefit>
2. ...

## Implementation Decisions

- 要构建/修改的模块
- 这些模块的接口
- 技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

注意：不要写具体文件路径或代码片段。

## Testing Decisions

- 好测试的标准（只测外部行为，不测实现细节）
- 哪些模块会被测试
- 代码库里已有的类似测试作为参考

## Out of Scope

明确排除的内容。

## Further Notes

其他备注。

五、关键规则

规则说明
不 interview，只合成 /to-spec 不再追问，它把已经讨论清楚的内容整理成文档。
用项目领域语言 spec 里应该使用 CONTEXT.md 里的术语，而不是通用编程词。
不写文件路径和代码片段 它们很快就会过时。例外：原型产出的决策性代码片段可以 inline。
User Stories 要足够长 覆盖功能的所有方面，不是象征性地列 3 条。
明确 Out of Scope 写出不做的事情和做同样重要。

六、Seams 是什么？

Seam（测试边界）是你可以测试的公共边界。好的 spec 应该明确说明：

  • 现有代码库里有哪些 seams 可以复用
  • 需要新增哪些 seams
  • 测试应该打在哪一层（单元、集成、端到端）

Seam 越少越好。理想情况整个功能通过一个公共接口就能测试。

记忆口诀

grill 磨想法，to-spec 写成文档。
不 interview，只合成；不写路径，不写代码。
User Stories 要长，Out of Scope 要明。
